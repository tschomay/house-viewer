Rotating github-actions-deployer

Swap the CI access key with no failed builds and no window where the pipeline has no working credential. Work top to bottom; your place is saved if you put the phone down.

First: these secrets are not in a9-tracker

I checked the repo you are sitting in. a9-tracker has no AWS anywhere in it — .github/workflows/deploy.yml deploys to Firebase Hosting and authenticates to Google through Workload Identity Federation, which is keyless by design. Its only Actions secrets are VITE_RECAPTCHA_SITE_KEY and VITE_APPCHECK_DEBUG_TOKEN, plus the variables GCP_WIF_PROVIDER and GCP_DEPLOY_SERVICE_ACCOUNT.

So AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY belong to a different repo. Name it below and every command and link on this page will point at the right place.

Two keys at once

An IAM user can hold exactly two access keys. That second slot is the whole trick: the new key works before the old one stops.

Secrets bind at job start

A job reads secret values when it starts. Changing a secret cannot disturb a run that is already going.

Deactivate before delete

Inactive is instantly reversible; deleted is forever. Every rollback on this page is a one-line flip back to Active.

Fill these in once

Everything below — commands, links, the trust policy — rewrites itself from these three. Saved in this browser.

Before you start

  • Run as yourself, not as the CI user. Step 1 prints who you are; if it comes back as github-actions-deployer, stop — you would be rotating the key out from under the shell you are using.
  • IAM permissions you need on that user: iam:ListAccessKeys, iam:GetAccessKeyLastUsed, iam:CreateAccessKey, iam:UpdateAccessKey, iam:DeleteAccessKey, plus cloudtrail:LookupEvents for step 2. Finding out at step 3 that you lack CreateAccessKey means waiting on someone else mid-rotation.
  • Admin on the GitHub repo. Only admins can write Actions secrets.
  • Tools: AWS CLI v2, jq, and the gh CLI signed in. No local setup? AWS CloudShell has the AWS CLI and jq ready and works on a phone; each step that needs gh has a console path.
  • Pick a quiet moment. You want to watch one full pipeline run go green before you disable anything. Not ten minutes before a release.
  1. 1

    See what keys the user already has

    You cannot plan the swap without knowing whether the second slot is free and which key the pipeline is actually using. One paste does all of it.

    cat > /tmp/rotate-1-inventory.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
USER_NAME=github-actions-deployer

echo "== Running as (must NOT be the CI user) =="
aws sts get-caller-identity --output table

echo
echo "== Access keys on ${USER_NAME} =="
aws iam list-access-keys --user-name "$USER_NAME" \
  --query 'AccessKeyMetadata[].[AccessKeyId,Status,CreateDate]' --output table

echo
echo "== Last time each key was used =="
for k in $(aws iam list-access-keys --user-name "$USER_NAME" \
             --query 'AccessKeyMetadata[].AccessKeyId' --output text); do
  echo "--- $k"
  aws iam get-access-key-last-used --access-key-id "$k" \
    --query 'AccessKeyLastUsed.[LastUsedDate,ServiceName,Region]' --output table
done
SH
bash /tmp/rotate-1-inventory.sh

    Read-only. Safe to run as many times as you like.

    What good looks like

    One key, Active, with a LastUsedDate from the last day or two. Put its ID into the Old access key ID box at the top of this page now — the rest of the steps need it and you should never have to retype it.

    If two keys are already listed

    The second slot is taken and step 3 will fail with LimitExceeded: Cannot exceed quota for AccessKeysPerUser: 2. Usually the extra one is a stale leftover from a previous rotation — check its LastUsedDate. If nothing has used it for weeks, clear the slot first:

    aws iam delete-access-key --user-name github-actions-deployer \
  --access-key-id AKIAOLDKEYEXAMPLE123

    Point that at the stale key ID, not the one in use. Deletion cannot be undone, so if you are unsure, set it --status Inactive first (step 6 has the command) and see if anything screams.

    If you see NoSuchEntity: The user with name github-actions-deployer cannot be found

    Your CLI is pointed at the wrong AWS account. Compare the account number in the first table against the account your pipeline deploys to, then re-run with the right profile: AWS_PROFILE=that-one bash /tmp/rotate-1-inventory.sh.

    If you see AccessDenied on ListAccessKeys

    Your own IAM identity is missing the permissions listed in "Before you start". Get them added before going further — a rotation abandoned halfway is worse than one not started.

  2. 2

    Find everything else using this key

    This is the step people skip and regret. An IAM user's key tends to spread: a second repo, a nightly job, a Terraform run, somebody's laptop from the week it was set up. Rotating breaks every one of them, and you find out days later. CloudTrail knows who has been calling with it.

    cat > /tmp/rotate-2-consumers.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
OLD_KEY_ID=AKIAOLDKEYEXAMPLE123

echo "== Callers seen using ${OLD_KEY_ID} (last 90 days, this region) =="
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue="$OLD_KEY_ID" \
  --max-results 50 \
  --query 'Events[].CloudTrailEvent' --output text \
  | jq -rR 'fromjson? | [.eventTime, .eventName, .sourceIPAddress, (.userAgent // "")[0:44]] | @tsv' \
  | sort -u
SH
bash /tmp/rotate-2-consumers.sh

    Read-only, safe to re-run. GitHub-hosted runners show up as Azure IP ranges with an aws-cli or aws-sdk user agent. A residential IP or a browser-ish agent is a human, and that human needs telling.

    What this will not show you

    Only the region you ran it in, only the last 90 days, and only management events — plain s3:PutObject traffic is invisible unless data events are switched on for that bucket. Empty output means "nothing found here", not "nothing uses this key". If you have workloads in other regions, re-run with AWS_REGION=eu-west-1 in front of the bash line.

    Also worth a look

    CloudTrail event history in the console, filtered by access key, is the same data with a date picker — easier on a phone than reading a wide table.

  3. 3

    Create the new key and write it straight into the repo secrets

    The new secret is displayed exactly once, ever. So don't display it: this script pipes it directly from the AWS API into gh secret set. It never lands on screen, never enters your shell history, and there is nothing for you to copy by hand.

    Nothing here disturbs the pipeline. The old key stays Active, and runs already in flight hold the old values until they finish.

    cat > /tmp/rotate-3-newkey.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
USER_NAME=github-actions-deployer
REPO=OWNER/REPO

command -v jq >/dev/null || { echo "jq is not installed"; exit 1; }
command -v gh >/dev/null || { echo "gh CLI is not installed - use the console path instead"; exit 1; }
gh auth status >/dev/null

COUNT="$(aws iam list-access-keys --user-name "$USER_NAME" \
           --query 'length(AccessKeyMetadata)' --output text)"
if [ "$COUNT" -ge 2 ]; then
  echo "STOP: ${USER_NAME} already has 2 access keys - AWS allows no more."
  echo "Clear the stale slot first (step 1), then re-run this."
  exit 1
fi

echo "==> Creating a second access key on ${USER_NAME}..."
NEW="$(aws iam create-access-key --user-name "$USER_NAME" --output json)"
NEW_ID="$(printf '%s' "$NEW" | jq -r '.AccessKey.AccessKeyId')"
NEW_SECRET="$(printf '%s' "$NEW" | jq -r '.AccessKey.SecretAccessKey')"
NEW=""
echo "    new key id: ${NEW_ID}"

echo "==> Waiting for it to go live (IAM is eventually consistent)..."
for attempt in 1 2 3 4 5 6; do
  if env -u AWS_SESSION_TOKEN -u AWS_PROFILE \
       AWS_ACCESS_KEY_ID="$NEW_ID" AWS_SECRET_ACCESS_KEY="$NEW_SECRET" \
       aws sts get-caller-identity >/dev/null 2>&1; then
    echo "    live"
    break
  fi
  echo "    not active yet, retrying in $((attempt * 5))s"
  sleep $((attempt * 5))
done

env -u AWS_SESSION_TOKEN -u AWS_PROFILE \
  AWS_ACCESS_KEY_ID="$NEW_ID" AWS_SECRET_ACCESS_KEY="$NEW_SECRET" \
  aws sts get-caller-identity --output table

echo "==> Writing both secrets on ${REPO}..."
printf '%s' "$NEW_ID"     | gh secret set AWS_ACCESS_KEY_ID     --repo "$REPO"
printf '%s' "$NEW_SECRET" | gh secret set AWS_SECRET_ACCESS_KEY --repo "$REPO"
NEW_SECRET=""

echo
echo "Done. ${NEW_ID} is in the repo secrets."
echo "The old key is still Active - nothing has broken yet, by design."
SH
bash /tmp/rotate-3-newkey.sh
    What good looks like

    An identity table showing arn:aws:iam::<account>:user/github-actions-deployer — proof the new key authenticates — then two lines from gh confirming both secrets were set. Note the new key ID down; step 5 uses it.

    Re-running this one is not free

    Every successful run creates a key, and there are only two slots. The guard at the top stops a blind second run. If the script died after creating the key but before writing the secrets, that key's secret is gone for good — delete it and start the step over:

    aws iam list-access-keys --user-name github-actions-deployer \
  --query 'AccessKeyMetadata[].[AccessKeyId,CreateDate]' --output table
# then, for the one created just now:
aws iam delete-access-key --user-name github-actions-deployer --access-key-id AKIA_THE_NEW_ONE

    No gh CLI? The console path

    Create the key in the IAM user's Security credentials tab (Create access key → Third-party service), then paste both values into the repo's Actions secrets, updating the two existing entries rather than making new ones.

    Deep links

    IAM › github-actions-deployer security credentials GitHub › Actions secrets OWNER/REPO
    Pasting by hand: the one thing that goes wrong

    The secret must land as a single line with no leading or trailing space and no line break. A wrapped copy that drags in a newline is invisible in the secrets UI and surfaces in CI as SignatureDoesNotMatch or The security token included in the request is invalid — both of which read like an AWS configuration problem and send you looking in entirely the wrong place. If you see either right after a manual paste, re-paste the secret; do not go debugging IAM policies.

  4. 4

    Make sure nothing is shadowing the secret you just set

    GitHub resolves a secret name at three levels, and the most specific wins: environment beats repository beats organization. If the workflow job declares environment: production and an environment secret of the same name exists, the repo secret you just wrote is ignored entirely and the pipeline keeps using the old key.

    cat > /tmp/rotate-4-scopes.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
REPO=OWNER/REPO
OWNER="${REPO%%/*}"

echo "== Repository secrets =="
gh secret list --repo "$REPO"

echo
echo "== Environment secrets (these WIN over repository secrets) =="
ENVS="$(gh api "/repos/${REPO}/environments" --jq '.environments[].name' 2>/dev/null || true)"
if [ -z "$ENVS" ]; then
  echo "(no environments)"
else
  for e in $ENVS; do
    echo "--- $e"
    gh secret list --repo "$REPO" --env "$e" || true
  done
fi

echo
echo "== Organization secrets =="
gh secret list --org "$OWNER" 2>/dev/null || echo "(personal account, or no org access)"

echo
echo "== Other workflows under ${OWNER} reading the same secret name =="
gh search code --owner "$OWNER" --filename '*.yml' 'AWS_ACCESS_KEY_ID' 2>/dev/null || true
SH
bash /tmp/rotate-4-scopes.sh

    Read-only, safe to re-run. Secret values are never shown — only names and when each was last updated, which is exactly what you need: the two you just wrote should carry today's date.

    If the pipeline still authenticates as the old key after step 3

    This is the cause nine times out of ten. Look for AWS_ACCESS_KEY_ID under an environment, and update it there too:

    gh secret set AWS_ACCESS_KEY_ID --repo OWNER/REPO --env production
gh secret set AWS_SECRET_ACCESS_KEY --repo OWNER/REPO --env production

    Run without --body, gh prompts for the value on a hidden line, so it stays out of your history.

    If another repo turned up in that last search

    It is sharing this one IAM user, and step 6 will break it. Either update its secrets the same way now, or give it its own IAM user before you deactivate anything.

  5. 5

    Run the pipeline and prove the new key is the one working

    Both keys are valid right now, which means a green build is not by itself proof — it could still be running on the old key from an environment secret you missed. The proof is AWS telling you the new key was used minutes ago.

    gh workflow list --repo OWNER/REPO
gh run list --repo OWNER/REPO --limit 5

    Then start one and watch it, putting your workflow's filename in place of deploy.yml:

    gh workflow run deploy.yml --repo OWNER/REPO
sleep 8
gh run watch --repo OWNER/REPO --exit-status

    If the workflow has no workflow_dispatch trigger there is no button to press — push a trivial commit, or hit Re-run jobs on the most recent run. A re-run resolves secrets fresh, so it picks up the new values.

    Then confirm which key did the work

    aws iam list-access-keys --user-name github-actions-deployer \
  --query 'AccessKeyMetadata[].AccessKeyId' --output text \
  | tr '\t' '\n' \
  | while read -r k; do
      printf '%s  ' "$k"
      aws iam get-access-key-last-used --access-key-id "$k" \
        --query 'AccessKeyLastUsed.LastUsedDate' --output text
    done
    What good looks like

    The new key ID carries a timestamp from the last few minutes; the old one is stuck at whenever it last ran. That, plus a green run, is the go-ahead for step 6.

    Give it a few minutes before you judge

    LastUsedDate is recorded with roughly fifteen-minute granularity and can lag. A blank or stale timestamp thirty seconds after a build is normal; wait and re-run the check rather than concluding the swap failed.

    If the run fails here

    You have lost nothing — the old key is still Active, so reverting is just putting the old key ID and secret back into the repo secrets, and the next run is green again. Two errors, two very different meanings: InvalidClientTokenId or SignatureDoesNotMatch means the credential itself is wrong (a bad paste, or the key not yet propagated — wait a minute and re-run). AccessDenied on a specific action means the credential is fine and the IAM policy is the problem — unrelated to the rotation, and not fixed by making another key.

    GitHub › Actions runs OWNER/REPO
  6. 6

    Deactivate the old key

    Until this runs, you have not rotated anything — you have added a key. The old one still opens every door, which is the situation you set out to end.

    aws iam update-access-key --user-name github-actions-deployer \
  --access-key-id AKIAOLDKEYEXAMPLE123 --status Inactive

aws iam list-access-keys --user-name github-actions-deployer \
  --query 'AccessKeyMetadata[].[AccessKeyId,Status]' --output table

    Idempotent — setting an already-inactive key to Inactive changes nothing and errors on nothing.

    What good looks like

    Two rows: the new key Active, the old one Inactive. Anything still holding the old key starts failing within seconds, which is the point: this is how you discover a consumer that steps 2 and 4 missed, at a moment when undoing it takes one command.

    Instant rollback

    Something unexpected went red? Flip it back and investigate afterwards. No new key needed, no secrets to re-enter.

    aws iam update-access-key --user-name github-actions-deployer \
  --access-key-id AKIAOLDKEYEXAMPLE123 --status Active
  7. 7

    Wait out a full cycle, then delete the old key

    Leave it Inactive long enough for every scheduled consumer to have had a turn — the nightly job, the weekly report, whatever has the longest interval. A day or two covers most setups. Nothing is at risk in the meantime: an inactive key grants nothing.

    When the soak is done, check that it really did go unused, then delete it:

    aws iam get-access-key-last-used \
  --access-key-id AKIAOLDKEYEXAMPLE123 \
  --query 'AccessKeyLastUsed.[LastUsedDate,ServiceName]' --output table

# Only if that timestamp predates the deactivation:
aws iam delete-access-key --user-name github-actions-deployer \
  --access-key-id AKIAOLDKEYEXAMPLE123
    Do not skip the deletion

    An IAM user gets two key slots. Leaving the dead key parked in one means your next rotation opens with LimitExceeded — usually discovered by whoever is rotating in a hurry after a leak. Clear the slot while you are already here.

    Deletion is final

    A deleted key ID never comes back; recovery means creating a different key and updating the secrets again. If the last-used timestamp is at all ambiguous, leave it Inactive another day — there is no cost to waiting.

  8. 8

    Stop having a key to rotatelater

    You have already built this exact thing once. a9-tracker's deploy workflow holds no Google credential at all: GitHub mints an OIDC token, Google exchanges it for a short-lived one, and scripts/setup-wif.sh provisioned it in an afternoon. AWS has the same mechanism, and it retires this runbook permanently.

    Three pieces: an IAM OIDC identity provider for token.actions.githubusercontent.com, a role that trusts only your repo, and a workflow that assumes it. The trust policy is the part worth getting exactly right — the sub condition is what stops any other repository on GitHub from assuming your role:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:OWNER/REPO:*"
        }
      }
    }
  ]
}

    Then the workflow drops both secrets and gains a role:

    permissions:
  id-token: write   # required to mint the OIDC token
  contents: read

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::ACCOUNT_ID:role/github-actions-deployer
      aws-region: us-east-1
    Order matters if you do this

    Get an OIDC run green before deleting the IAM user's keys, exactly as steps 5 to 7 do here. Ask me and I will write the AWS setup script the way scripts/setup-wif.sh does for Google — idempotent, re-runnable, with the propagation retries already in it.
