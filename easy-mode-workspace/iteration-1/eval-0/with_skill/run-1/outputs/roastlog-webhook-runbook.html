Wiring Stripe into Roastlog

Your endpoint is already live at api.roastlog.dev/webhooks/stripe and handles two events. Everything left is dashboard clicking. Tap a step to cross it off — your place is saved if you put the phone down.

Before you start

  • Use the browser dashboard, not the Stripe mobile app — the app can’t create webhook endpoints. If Safari or Chrome hands you off to the app, use “Request desktop site”.
  • You need to be the account owner or have the Developer / Administrator role. A read-only teammate sees the webhooks page but the create button is greyed out.
  • You need a way to set an environment variable on whatever hosts api.roastlog.dev, and to redeploy it. If you can’t reach your host from your phone, do steps 1–4 now and step 5 later.
The thing that trips everyone

Test mode and live mode are two separate worlds. You create the endpoint twice, and each one gives you a different signing secret. A test secret will never verify live traffic — it fails with a signature error that looks like a code bug.

Test modeSteps 1–6
  1. 1 Open the webhooks page in test mode
    Stripe › Workbench › Webhooks (test)

    Check the top of the screen actually says Test mode before doing anything. The link forces it, but a saved session can bounce you back to live.

    If that page 404s

    Older accounts haven’t been moved to Workbench yet. Use dashboard.stripe.com/test/webhooks instead — same thing, older layout.

  2. 2 Add the destination URL

    Tap Create an event destination (older layout: Add endpoint), choose Webhook endpoint if it asks how to receive events, and paste this as the endpoint URL:

    https://api.roastlog.dev/webhooks/stripe

    Description is optional — “Roastlog API” is enough. Leave the API version on the default unless your Stripe library is pinned to an older one.

    Order varies

    Some accounts ask you to pick events first and the URL second. If you see an event picker before a URL field, do step 3 and come back here.

  3. 3 Select exactly these two events

    In the event picker, paste each name into the search box and tick the exact match. Don’t use “select all events” — it floods your endpoint with types it will just log and ignore.

    checkout.session.completed
    invoice.payment_failed

    Then create the destination. The list stays editable afterwards, so a mistake here is a two-tap fix later.

    Worth knowing about the second one

    invoice.payment_failed only ever fires for invoices and subscriptions. If Roastlog takes one-off Checkout payments, it will stay silent forever — the events you’d actually want are checkout.session.async_payment_failed and payment_intent.payment_failed. Add them here if that’s your setup.

  4. 4 Copy the signing secret

    On the destination’s page, find Signing secret and tap Reveal. It starts with whsec_ followed by a long string. Use Stripe’s own copy control if it offers one rather than selecting the text by hand.

    This is the one value I can’t pre-fill for you

    It has to land in your host as one line, no spaces, no line break. If a break sneaks in, Stripe rejects every delivery with No signatures found matching the expected signature for payload — which reads like a bug in your verification code, but is almost always a paste that got wrapped.

    This secret belongs to this endpoint in this mode only. Rotating it, or deleting and recreating the endpoint, gives you a new one.

  5. 5 Set it on your API host, then redeploy

    Add it as an environment variable on whatever runs api.roastlog.dev. Unless your code already reads a different name, use:

    Variable name

    STRIPE_WEBHOOK_SECRET
    Don’t skip this half

    Vercel, Render, Railway, Fly and friends only pick up a new variable on the next deploy. Saving it changes nothing on the running instance. Trigger a redeploy even though no code changed, or every delivery in step 6 will fail with a signature error.

  6. 6 Send a test event and read the delivery

    Back on the destination page, open the overflow menu (…) and choose Send test event. Pick checkout.session.completed and send it. Then open the Event deliveries tab.

    What good looks like

    The delivery shows HTTP 200 within a second or two, and expanding it shows your endpoint’s response body. Anything else — 3xx, 4xx, 5xx, or “timed out” — see When it breaks below.

    Every delivery has a Resend button. Resending is safe and it’s the fastest loop: fix, redeploy, resend, refresh.

Live modeSteps 7–8
  1. 7 Do steps 1–5 again in live mode
    Stripe › Workbench › Webhooks (live)

    Same URL, same two events — the values below are the identical ones from steps 2 and 3, here so you don’t have to scroll back:

    https://api.roastlog.dev/webhooks/stripe
    checkout.session.completed
    invoice.payment_failed
    The secret is different

    This endpoint issues its own whsec_ value. Put that one in your production environment — the same variable name, a different value from the test one — and redeploy production.

    Live mode may also require your account to be activated (business details, bank account) before it will accept real payments at all. Stripe will tell you on this screen if it isn’t.

  2. 8 Confirm with one real event

    Make one small real purchase (refund it after), or wait for the next genuine one, then check Event deliveries on the live destination. You want a 200 there within a minute.

    If it fails now

    You have breathing room: Stripe retries failed live deliveries with exponential backoff for up to three days, so fixing the endpoint today still gets the event through. But an endpoint that keeps failing for days gets disabled automatically and you’ll get an email — don’t ignore that one.

When it breaks

400 · No signatures found matching the expected signature for payload

Means the secret is wrong for this mode, or your handler verified against an already-parsed body. Check you used the test secret for the test endpoint; then check that the JSON body parser doesn’t run before verification on this route — Stripe signs the raw bytes, and express.json() destroys them.

400 · Timestamp outside the tolerance zone

Means your server’s clock is more than five minutes off, or you’re replaying an old captured payload. Fix the clock; don’t widen the tolerance.

301 / 302 / 307 in the delivery log

Means Stripe hit a redirect — usually a trailing-slash or www rule — and it does not follow redirects, so this counts as a failed delivery. Register the exact final URL instead.

404 or 405 from your own API

Means the path or method is off. Stripe always POSTs. Confirm the route is POST /webhooks/stripe and not gated behind auth middleware that expects a session.

Timed out

Means you did the work before responding. Return 200 immediately, then process — queue it, or fire the side effects after the response. Stripe gives up on a slow endpoint and retries, which turns one order into several.

200, but nothing happened in your app

Means your handler acknowledged an event it doesn’t branch on, or the checkout wasn’t actually paid. On checkout.session.completed, check payment_status === "paid" before granting anything — delayed payment methods complete the session first and pay later.

The same event arrives twice

Means normal Stripe behaviour, not a bug. Deliveries can duplicate and can arrive out of order. Record event.id and ignore ids you’ve already processed.

Later, at a laptop

Two things worth doing once you’re off the phone. Neither is required to finish the setup above.

Smoke-test the deployed endpoint — safe to re-run

cat > /tmp/roastlog-webhook-check.sh <<'EOF'
#!/usr/bin/env bash
set -u
URL="https://api.roastlog.dev/webhooks/stripe"
echo "POST $URL with an unsigned body - expecting 400 from signature verification"
curl -sS -o /tmp/roastlog-webhook-body.txt \
  -w 'status:   %{http_code}\nredirect: %{redirect_url}\n' \
  -X POST "$URL" \
  -H 'Content-Type: application/json' \
  -d '{"id":"evt_00000000","type":"ping"}'
echo "--- first 400 bytes of the response ---"
head -c 400 /tmp/roastlog-webhook-body.txt
echo
EOF
bash /tmp/roastlog-webhook-check.sh
What good looks like

status: 400 and a signature-verification message. That is the success case here: it proves the route exists, accepts POST, and is checking signatures. A 404 means the path is wrong; a non-empty redirect: line means Stripe will fail on a redirect; a 200 on an unsigned body means verification isn’t running at all — anyone could forge an order.

Replay real event shapes against localhost

Install the Stripe CLI, then run these one at a time — stripe login opens a browser to approve, and stripe listen holds the terminal open, so trigger needs a second tab.

stripe login
stripe listen --forward-to localhost:3000/webhooks/stripe
stripe trigger checkout.session.completed
Different secret again

stripe listen prints its own whsec_ on startup, unrelated to either dashboard endpoint. Use that one in your local .env, and it changes each time unless you pass --api-key with a fixed key.
